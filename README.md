# Лабораторная работа: умный указатель SmrtPtr

Учебная реализация умного указателя `SmrtPtr<T>` с подсчётом ссылок. Работа включает сравнение времени выполнения операций и расхода памяти с обычным указателем `int*` и `std::shared_ptr<int>`.

## Реализация

`SmrtPtr` хранит адрес объекта и идентификатор записи в централизованном хранилище `global_storage`. Запись `Storage` содержит адрес ресурса, счётчик ссылок, размер, признак массива и функцию удаления. Для хранения записей используется `MutableArraySequence`.

Копирование создаёт ещё одного владельца ресурса и увеличивает счётчик ссылок. Перемещение передаёт владение и оставляет источник пустым. Когда освобождается последняя ссылка, управляемый объект удаляется.

## Методика нагрузочных тестов

- Язык и компилятор: **C++20, clang++**.
- Параметры сборки: `-std=c++20 -Wall -Wextra -Iinclude -O2`.
- Размеры нагрузки: **1 000, 10 000, 100 000 и 1 000 000**.
- Время: `std::chrono::high_resolution_clock` с переводом длительности в целые микросекунды.
- Для каждой временной точки выполнено **пять прогонов**. В основных таблицах приведено арифметическое среднее всех пяти значений, без исключения первого запуска или выбросов.
- Память: `sizeof` и **Peak RSS** процесса на macOS.
- В тестах используются отдельно выделенные `int`; `std::shared_ptr` создаётся из `new int(...)`, без `std::make_shared`.

Время указано в **микросекундах (µs) за весь измеряемый участок**, а не за одну операцию. Для временных тестов `N` — число итераций; для тестов памяти — число одновременно живых объектов.

### Измеряемые операции

| Тест | Содержимое измеряемого участка |
|---|---|
| CREATE | Создание и уничтожение объекта на каждой итерации. В варианте RawPtr дополнительно выполняется накопление значения в `volatile long long sum`. |
| COPY CONSTRUCTOR | Создание исходного владельца, затем `N` временных копий. Каждая копия уничтожается в конце итерации; исходный владелец — после остановки таймера. |
| COPY ASSIGNMENT | Создание `source` и `target`, затем повторное `target = source`. После первого присваивания оба указателя разделяют один ресурс. Итоговое уничтожение владельцев находится вне таймера. |
| MOVE CONSTRUCTOR | Перемещение каждого заранее подготовленного источника во временный указатель и уничтожение этого указателя вместе с ресурсом в конце итерации. |
| MOVE ASSIGNMENT | Перемещение из заранее подготовленного источника в непустой получатель, включая освобождение прежнего ресурса получателя. |

В MOVE-тестах векторы заполняются до запуска таймера, ёмкость резервируется через `reserve(n)`. Измерения выполняются последовательно: SmrtPtr, затем std::shared_ptr; в CREATE между ними проверяется RawPtr.

Для RawPtr сравнивается CREATE и расход памяти. Копирование адреса не выполняет подсчёт ссылок и передачу владения, поэтому отдельные COPY/MOVE-результаты для него не приводятся.

### Интерпретация измерений

CREATE и MOVE CONSTRUCTOR включают уничтожение ресурсов; их результаты характеризуют полный описанный сценарий, а не изолированный вызов конструктора. COPY ASSIGNMENT в основном измеряет повторное присваивание уже разделяемого ресурса.

В CREATE вариант RawPtr отличается использованием `volatile`-аккумулятора. Наблюдаемые обращения к нему не гарантируют сохранения всех выделений памяти после оптимизации. Поэтому время RawPtr не следует интерпретировать как чистую стоимость `new/delete`. Значение `0 µs` в отдельном прогоне соответствует нулю после перевода длительности в целые микросекунды и не означает отсутствия затрат.

Результаты относятся к однопоточным тестам данной реализации. Разброс запусков приведён в исходных данных в конце отчёта.

## Размер объектов: sizeof

| Тип | Размер, байт |
|---|---:|
| `int*` | 8 |
| `SmrtPtr<int>` | 16 |
| `std::shared_ptr<int>` | 16 |
| `Storage` | 40 |

`sizeof` отражает размер самого объекта типа и не включает внешние динамические выделения. У SmrtPtr одна запись Storage приходится на управляемый ресурс, а не на каждую копию указателя. У std::shared_ptr служебный блок также не входит в размер обёртки.

Поэтому одинаковый размер обёрток — **16 байт** — не означает одинакового общего потребления памяти.

### Сравнение на 1 000 000 операций

Отношение `t(std::shared_ptr) / t(SmrtPtr)` больше единицы означает меньшее среднее время у SmrtPtr в данном сценарии.

| Тест | SmrtPtr, µs | std::shared_ptr, µs | Отношение времени |
| --- | ---: | ---: | ---: |
| CREATE | 33 682.6 | 34 758.2 | 1.03 |
| COPY CONSTRUCTOR | 2 486.4 | 5 633.0 | 2.27 |
| COPY ASSIGNMENT | 3 748.4 | 5 990.8 | 1.60 |
| MOVE CONSTRUCTOR | 12 641.8 | 18 127.4 | 1.43 |
| MOVE ASSIGNMENT | 12 229.0 | 20 723.0 | 1.69 |

На миллионе операций средние CREATE близки: **33.68 ms** у SmrtPtr и **34.76 ms** у std::shared_ptr. В COPY CONSTRUCTOR среднее время SmrtPtr меньше примерно в **2.27 раза**, в COPY ASSIGNMENT — в **1.60 раза**, в MOVE CONSTRUCTOR — в **1.43 раза**, в MOVE ASSIGNMENT — в **1.69 раза**. Эти отношения описывают выбранные сценарии и не устанавливают общего превосходства реализации.

## Результаты измерения памяти

Peak RSS измеряется командой `/usr/bin/time -l` по полю `maximum resident set size` в байтах. Для каждой пары «тип указателя — N» используется отдельный процесс.

Сначала вектор резервирует место и сохраняет указатели на `N` одновременно живых объектов `int(5)`. Затем ресурсы освобождаются: для RawPtr — циклом `delete`, для умных указателей — при уничтожении вектора. Освобождение в конце теста не уменьшает уже достигнутый пик RSS.

На размерах 1k, 10k и 100k приведено среднее трёх запусков. На 1M используется итоговый замер для каждой реализации. **1 MiB = 1 048 576 байт**.

| N | RawPtr, MiB | SmrtPtr, MiB | std::shared_ptr, MiB |
| --- | ---: | ---: | ---: |
| 1 000 | 1.36 | 1.50 | 1.41 |
| 10 000 | 1.59 | 2.75 | 1.99 |
| 100 000 | 3.65 | 13.35 | 7.48 |
| 1 000 000 | 24.33 | 110.27 | 62.63 |

Peak RSS учитывает память всего процесса: объекты, контейнеры, служебные структуры, расходы аллокатора и другие резидентные страницы. Базовая память процесса из результатов не вычитается.

При миллионе одновременно живых объектов SmrtPtr занимает в пике **110.27 MiB**, std::shared_ptr — **62.63 MiB**, RawPtr — **24.33 MiB**. Пик SmrtPtr примерно в **1.76 раза** выше std::shared_ptr и в **4.53 раза** выше RawPtr.

У SmrtPtr дополнительная память расходуется на записи Storage и ёмкость централизованного хранилища. Миллион записей по 40 байт требует около **38.15 MiB** только для самих записей, без обёрток, управляемых объектов и остальных расходов.

## Сборка и запуск

Для запуска нагрузочных тестов в `tests/load_test.cpp` нужно включить соответствующие вызовы в `main()`. Для выбранного временного сценария используются четыре значения N: `1000`, `10'000`, `100'000`, `1'000'000`.

Нагрузочный файл содержит собственный `main()` и может собираться отдельно, без GoogleTest:

```bash
clang++ -std=c++20 -Wall -Wextra -Iinclude -O2 tests/load_test.cpp -o tests_run
./tests_run
```

Повторить запуск пять раз для получения серии измерений. После изменения включённых тестов файл необходимо пересобрать.

Для памяти оставить в `main()` один вызов: `TestRawMemory(N)`, `TestSmrtPtrMemory(N)` или `TestSharedPtrMemory(N)`. После сборки выполнить:

```bash
/usr/bin/time -l ./tests_run
```

Каждую реализацию и размер проверять отдельным запуском. Режимы AddressSanitizer и проверки утечек предназначены для диагностики и не используются для сопоставления с приведёнными результатами сборки `-O2`.

## Выводы

1. SmrtPtr и std::shared_ptr имеют одинаковый размер обёртки — **16 байт**, однако централизованное хранилище увеличивает общий расход памяти SmrtPtr.
2. В измеренных COPY- и MOVE-сценариях SmrtPtr показывает меньшее среднее время на всех четырёх размерах нагрузки.
3. В CREATE на миллионе итераций средние результаты умных указателей близки; разброс отдельных запусков не позволяет считать небольшую разницу устойчивым преимуществом.
4. По Peak RSS на всех размерах выполняется **RawPtr < std::shared_ptr < SmrtPtr**.
5. Реализация демонстрирует компромисс между временем обслуживания указателей и расходом памяти. Результаты однопоточных тестов не подтверждают равенство гарантий потокобезопасности собственной и стандартной реализации.
